# lust design

Lust is a Rust-like language. It gives up some expressiveness to get very fast check and build times. The main user is a coding agent that runs `check` hundreds of times per task.

Status: plan, revision 6. The prototype exists (about 11k lines, see [README](README.md)). Cold compiles are [measured](#speed-of-light-prototype-phase-05) (the numbers in that section predate the incremental work; current cold results are in the README), and an [incremental daemon](#incremental-daemon-phase-7-early) makes an agent's edit loop 130x faster than rustc. Two review rounds by `Muse Wonder Full` and `gpt-6.1-sol` are in the [Review log](#review-log). Both reviewers say the plan is ready for Phase 0 and the Phase 1 pilot. Phase 2 starts only after Phase 0 confirms the speed assumptions.

Scope stance: big is fine. macOS is a first-class target. If the best path is to fork `tcc` or write our own backend, we do it. We pick the path from measurements, not from its size.

## Where the speed comes from

Rust spends time in different places for `check` and for `build`. Lust attacks each one separately.

| Cost in Rust | Affects | What lust does |
|---|---|---|
| Proc macros must compile, run, and parse tokens | check, build | No user macros. A fixed set of built-in macros and derives. |
| Trait solving can search, backtrack, and recurse | check | Each trait obligation has at most one candidate impl. No search. |
| LLVM, even at `-O0` | build | Dev builds emit C and compile it with `tcc`. |
| Linking many large object files | build | Few, small objects. `tcc` links them itself. |
| One crate checks mostly in sequence | check | Files check in parallel. Signatures are always explicit. |

Borrow checking is a real cost. On our idiomatic benchmark, rustc's "MIR build + borrow check" pass takes 42% of `check` time (see [Evidence](#evidence-for-the-speed-claim)). Rust checks one function body at a time, using callee signatures at call sites. Lust does the same, but it must run its borrow checker on a simple, flat IR, not through a full MIR pipeline. The "no references in structs" rule keeps the checker smaller and removes lifetime syntax for agents. It is not a speed rule by itself.

Phase 0 must confirm this table. We profile ts-rust and look at `check` and `build` separately.

### tcc spike (done)

Machine: 24-core x86_64 Linux.

| Input | Tool | Time |
|---|---|---|
| 400k lines of generated C (25k functions, structs, switches, overflow checks), one file | `tcc` 0.9.27 (Debian, 2020 snapshot) | 0.55 s |
| same | `tcc` 0.9.28rc mob (2026-10-03) | 0.49 to 0.62 s |
| same | `tcc` mob `-g` | 0.67 s |
| same | `gcc -O0` | 44 s |
| one 16.7k-line shard | `tcc -c` | 0.04 s |

Also found:

- `tcc` mob has macOS arm64 and Mach-O support, DWARF debug info, and `stdatomic.h`. Its upstream CI runs on `macos-15` (arm64), `macos-15-intel`, Linux, and Windows. It is active: about 200 commits since August 2025.
- Debian's 0.9.27 has no `stdatomic.h`. Mob has it, and it works.
- Neither version has `__builtin_add_overflow`. Lust emits its own overflow checks, or our fork adds the builtins.

Result: `tcc` is fast enough that lust **plans to monomorphize all generics**, the same as Rust. Dictionary-passing generics are plan B.

Limits of this spike. It only measures `tcc` on C that already exists. It does not measure:

- how much C a real program makes after monomorphization. Each closure is its own type, so iterator-heavy code makes many instances. A reviewer measured 84k mono functions from 32k lines of Rust.
- the time to parse, check, find instances, and write C.
- link time.
- run speed. `tcc` does not inline, so each iterator adapter is a call per element. Dev binaries will be slower than Rust dev binaries.

Phase 0 adds a mono-size spike to measure these, on Linux and on macOS arm64.

## Evidence for the speed claim

Goal: 100x faster than rustc for `check` and dev builds. Status: **met for edit loops on the supported subset.** An agent's edit loop on a realistic 31k-line crate is 130x faster than rustc in its best incremental setup (see [Incremental daemon](#incremental-daemon-phase-7-early)). Cold compiles are 20x to 55x faster. The idiomatic shape (generics, closures, iterators) is not measured yet.

### rustc baseline (measured)

Machine: 24-core x86_64 Linux, rustc 1.99.0. One crate, one file, generated by [`bench/rustc-baseline`](bench/rustc-baseline). Every program is valid lust, so the same file can go to both compilers later.

- **plain:** structs, enums, `match`, `Vec`, `String`, `format!`. No generics or closures.
- **idiomatic:** iterator chains with closures, `Result` and `?`, `HashMap::entry`, a trait, and a generic function.
- **edit:** change one constant in one function body, then run again with the incremental cache.

| Shape | Lines | Check cold | Check after edit | Debug build cold | Debug build after edit |
|---|---|---|---|---|---|
| plain | 9.6k | 3.45 s | 1.21 s | 5.35 s | 2.32 s |
| idiomatic | 10.1k | 4.69 s | 1.03 s | 12.35 s | 2.18 s |
| plain | 48k | 17.4 s | 6.71 s | 26.9 s | 11.6 s |
| idiomatic | 50.4k | 37.1 s | 6.28 s | 72.1 s | 13.1 s |

rustc's best case. The cold numbers above use the incremental cache, which is slow for a cold run. Without it, or with the parallel front end (`-Z threads=8`), rustc is about 3x faster: plain 48k `check` takes 5.75 s, not 17.4 s. Idiomatic `check` takes 1.02 s at 10k lines and 9.3 s at 50k lines with `-Z threads`. All comparisons below use rustc's best configuration.

Where `check` time goes (idiomatic, 10k lines, `-Z time-passes`): MIR build + borrow check 42%, type check 41%, coherence 7%, parse and macro expansion 2%. Proc macros cost nothing here because the benchmark has none. Real crates that use `serde` will show more macro time.

What 100x means against the best rustc numbers above:

| Shape | Operation | rustc | 100x target |
|---|---|---|---|
| idiomatic 50k | check cold | 9.3 s | 93 ms |
| idiomatic 50k | check after edit | 6.3 s | 63 ms |
| idiomatic 50k | debug build cold | 72 s | 720 ms |
| idiomatic 50k | debug build after edit | 13.1 s | 131 ms |

Caveat: one big crate is a bad case for rustc. Real projects split code into many crates, and cargo builds them in parallel. The fair baseline must also include a workspace version of each program.

### How we prove it

1. **Same input.** The same `.rs` files go to rustc and to lust. Rule zero makes this possible.
2. **rustc at its best.** Compare with the faster of these: one crate with `-Z threads`, and a workspace of many crates built with `cargo -j`. Both with and without incremental.
3. **Same strictness.** Lust must reject the same invalid programs as rustc, on a negative corpus. A checker that skips checks is fast for no reason. This stops that.
4. **Each stage on its own.** Report parse, check, instance discovery, codegen, and link, cold and after a one-line edit, on both tier 1 platforms.
5. **Real code too.** Port part of ts-rust to the subset and measure it, not only generated code.
6. **Claim only what we measured.** Each shape gets its own number. "100x" is only stated for the shapes that reach it.

### Speed-of-light prototype (Phase 0.5)

Built. 8.6k lines of Rust and C. It compiles the **plain** shape end to end: a parallel lexer and parser, a type checker, lowering to a MIR-like IR, a borrow checker, a C backend, and `tcc`. The test suite has 34 programs: output matches rustc, rustc and lust reject the same invalid programs, and every generated program runs clean under ASan and UBSan.

Results on the same file, rustc in its best configuration (`bench/compare.sh plain 640 3200`):

| Lines | Operation | rustc | lust | Speedup |
|---|---|---|---|---|
| 9.6k | check | 1.36 s | 33 ms | 41x |
| 9.6k | debug build | 2.57 s | 110 ms | 23x |
| 48k | check | 5.75 s | 73 ms | 79x |
| 48k | check after a one-line edit | 6.64 s | 73 ms | 91x |
| 48k | debug build | 12.1 s | 266 ms | 45x |
| 48k | build, no debuginfo | 12.1 s | 218 ms | 56x |

Where lust's time goes, 48k-line build (wall time on 24 cores):

| Stage | Time | Notes |
|---|---|---|
| lex + parse | 32 ms | 48 chunks in parallel, then merged by index shifting |
| collect | 11 ms | the only serial semantic stage |
| typeck + lower + borrowck | 22 ms | per function, in parallel. CPU time: typeck 71 ms, lower 116 ms, borrowck 278 ms |
| C codegen + assembly | 38 ms | per function, then per shard |
| tcc compile | 72 ms | 19 shards in parallel `tcc -c` processes |
| link | 17 ms | libtcc, in process |

What we learned:

1. **The rustc baseline was too kind to us at first.** Incremental mode makes rustc's cold runs about 3x slower. Against rustc's best configuration, the honest speedup is 40x to 90x, not "100x and more".
2. **The borrow checker is the most expensive front-end stage.** It uses 60% of front-end CPU time. This matches the rustc profile (MIR build + borrow check is 42%). It is the next optimization target.
3. **The allocator matters a lot.** Switching to mimalloc made `check` 2.5x faster, because glibc malloc fights over a kernel lock with 24 threads.
4. **libtcc compiles one unit at a time,** behind a global lock. Parallel `tcc -c` processes on C shards work around it. A lock-free fork or a native backend (Phase 8) would remove the process cost.
5. **Generated C size drives build time.** Trimming the C by 2x (grouped declarations, plain literals, no dead blocks, per-shard declarations) cut `tcc` time by 2x.
6. **Small programs pay fixed costs.** At 10k lines the speedup is lower (23x to 41x), because process startup, thread startup, and the per-shard runtime header dominate.

Not proven yet:

- The idiomatic shape. Generics, closures, and iterators monomorphize into much more C. This is the biggest open risk for the build number.
- macOS arm64. No timing run on a Mac yet.
- Real code. ts-rust uses many features the prototype does not have.
- "After edit" speed. lust has no incremental mode. A warm daemon (Phase 7) should turn the 73 ms into a few ms, which is where 100x+ becomes easy.

### Incremental daemon (Phase 7, early)

Built, because cold compiles alone did not reach 100x. `lust daemon` keeps a warm session per file. The `lust` command is a thin client (no custom allocator, about 1 ms to start) that sends the request over a Unix socket, or runs `lust-core` cold if no daemon answers.

Benchmark: `bench/realish/agent_loop.py`. A 784-line warehouse service (inventory, an order state machine, a pricing-rule language with a tokenizer, parser, and evaluator, shortest paths with a binary heap, reports) cloned into 40 modules: 31k lines. Twelve agent-style edits: behavior changes, a new function, and two mistakes that both compilers must reject. rustc runs with `-Z threads=8`, `-C incremental`, and `-C debuginfo=0`, its fastest setup on this machine. After each edit, both compilers must agree on pass or fail, and the programs must print the same output.

| | rustc | lust | Speedup |
|---|---|---|---|
| 12 checks | 12.80 s | 0.101 s | 127x |
| 10 builds | 20.45 s | 0.155 s | 132x |
| Edit loop (checks + builds) | 33.25 s | 0.255 s | 130x |
| Program runs (10) | 131 ms | 219 ms | 0.6x |

A typical edit: lust checks in 6 to 9 ms and builds in 14 to 18 ms. rustc takes 0.8 to 1.3 s to check and 1.1 to 2.5 s to build.

How it works:

1. **Edit window.** Compare the new source with the last one (two `memcmp`s). Chunks of whole items before and after the changed bytes are reused (tokens and scan results); only the window is split and lexed. Chunk boundaries are content-defined (a hash of each item's header line), so inserting a function does not move them.
2. **Token-level scan.** For each function: a hash of its body tokens. For each top-level item: a hash of its tokens outside bodies. No positions, so moving code changes nothing.
3. **Three cases.** Bodies only: parse, check, and lower just those bodies, into the existing AST. Top-level functions added, removed, or changed signature: parse just the changed chunks and splice their items in; re-check those functions and every body that mentions one of their names. Anything else: full rebuild.
4. **Stable slots.** Each function gets a slot keyed by its name (and impl type). Cached C, objects, and the function table use slots, so adding a function does not invalidate the others.
5. **No full relink.** Every call goes through `lust_fns[slot]`. The first build links all units into `libbase.so`. Each edit compiles only the changed unit as an overlay, then links a small executable (main plus overlays) against `libbase.so`. At startup the overlays overwrite their table entries. After 32 overlays, the base is rebuilt.
6. **Position-free code.** Panic locations are stored as (slot, line within the function, column); a per-build line table turns them into file lines.

Costs and limits:

- Indirect calls and tcc's unoptimized code make programs run about 1.7x slower than rustc's debug builds. Inline overflow checks, direct calls in release mode, and a better backend (Phase 8) are the fixes.
- A change to a type or an impl block is a full rebuild (about 50 ms check, 100 ms build at 31k lines). Still 25x faster than rustc, but not 100x.
- Daemon builds are not standalone: they load `libbase.so` from the daemon's cache directory. A cold `lust build` links a standalone executable.

## Rule zero: lust is a Rust subset

Every valid lust program is also a valid Rust program. For the cases below, it has the same behavior.

Why:

1. **Agents already know Rust.** Training data gives a free prior.
2. **rustc is a free test oracle.** We compile each test program with both `lust` and `rustc`, then compare.
3. **Free release builds.** `rustc -O` works on any lust program. This is the release path.

### The exact contract

- Oracle: `rustc 1.99.0`, edition 2024, targets `x86_64-unknown-linux-gnu` and `aarch64-apple-darwin`.
- Dev oracle flags: `-C panic=abort -C overflow-checks=on -A unconditional_panic`. This is the single-file oracle (`lust build main.rs`, difftest). A Cargo crate target (`lust build src/main.rs --manifest-path Cargo.toml`) is compared with `cargo build` instead: it follows the dev profile's `panic` setting (Cargo's default is unwind) and its `debug-assertions`, and rejects `overflow-checks = false`. Release oracle flags: `-C panic=abort -C overflow-checks=off -O -A unconditional_panic`. Without `-A unconditional_panic`, rustc rejects code like `[1, 2][5]` at compile time, but lust aborts at run time.
- **Compared:** stdout, and exit status (success or abort).
- **Not compared:** panic message text and location, `HashMap` and `HashSet` iteration order, thread interleaving, `{:p}` output.
- Corpus programs must not let map order reach the output in any way. This includes `keys().next()` and the drop order of map values. Check: run the rustc binary 3 times. Rust seeds `HashMap` per process, so if the outputs differ, the program is not allowed in the corpus.
- Lust's `HashMap` uses a fixed seed. Its order is stable from run to run, but it is not the same order as Rust's.
- Drop order is the same as Rust's. This includes temporaries, early `return`, and `?`. Differential tests check it with `Drop` impls that print.
- Float `Display` and `Debug` match Rust byte for byte. Tested on rustc 1.99: `1.0` prints `1` with `Display` and `1.0` with `Debug`. `1e21` prints all its digits with `Display` and `1e21` with `Debug`. The runtime needs a shortest round-trip printer (Ryu style), and a float parser with correct rounding.

The cost: the lust std must copy the Rust std API for the parts we support.

## Syntax sample

```lust
use std::collections::HashMap;

#[derive(Debug, Clone, PartialEq)]
enum Kind {
    Tool,
    Food { expires_in_days: u32 },
}

#[derive(Debug, Clone)]
struct Item {
    name: String,
    kind: Kind,
    count: u32,
}

#[derive(Debug)]
enum ParseError {
    MissingField(String),
    BadNumber(String),
}

// Parses "name,count" or "name,count,days".
fn parse_item(line: &str) -> Result<Item, ParseError> {
    // `Vec<&str>` is fine: std types can hold borrows. User struct fields cannot.
    let parts: Vec<&str> = line.split(',').map(|p| p.trim()).collect();
    let name = parts.get(0).ok_or(ParseError::MissingField("name".to_string()))?;
    let count_text = parts.get(1).ok_or(ParseError::MissingField("count".to_string()))?;
    let count = count_text
        .parse::<u32>()
        .map_err(|_| ParseError::BadNumber(count_text.to_string()))?;

    let kind = match parts.get(2) {
        Some(days) => Kind::Food {
            expires_in_days: days.parse().map_err(|_| ParseError::BadNumber(days.to_string()))?,
        },
        None => Kind::Tool,
    };

    Ok(Item { name: name.to_string(), kind, count })
}

// Sums the count of each item name.
fn totals(items: &[Item]) -> HashMap<String, u32> {
    let mut out = HashMap::new();
    for item in items {
        *out.entry(item.name.clone()).or_insert(0) += item.count;
    }
    out
}

trait Describe {
    fn describe(&self) -> String;
}

impl Describe for Item {
    fn describe(&self) -> String {
        match &self.kind {
            Kind::Tool => format!("{} x{}", self.name, self.count),
            Kind::Food { expires_in_days } => {
                format!("{} x{} (expires in {} days)", self.name, self.count, expires_in_days)
            }
        }
    }
}

// Generic function. Monomorphized, the same as Rust.
fn print_all<T: Describe>(things: &[T]) {
    for thing in things {
        println!("{}", thing.describe());
    }
}

fn main() {
    let input = "hammer, 2\napple, 5, 3\nhammer, 1";
    let items: Vec<Item> = input.lines().filter_map(|l| parse_item(l).ok()).collect();
    print_all(&items);
    println!("{:?}", totals(&items).get("hammer"));
}

#[test]
fn parses_food() {
    let item = parse_item("apple, 5, 3").unwrap();
    assert_eq!(item.kind, Kind::Food { expires_in_days: 3 });
}
```

## Borrow model

Rust's model with no lifetime names in user code.

- The checker works on one function body at a time. At a call site, it uses the callee's signature. This is the same as Rust.
- User `struct` and `enum` definitions cannot have reference fields or lifetime parameters.
- **User generic types cannot take a type argument that carries a borrow.** `Wrapper<&str>` is rejected. This avoids variance and drop-check rules for user types. Rust allows it, so this is a deliberate limit.
- Std types can carry borrows: `&T`, `Vec<&str>`, `Option<&T>`, `HashMap<&str, u32>`, iterators, closures that capture by reference, `MutexGuard`, and `Entry`. These can be locals, parameters, and return values.
- Signatures use Rust's elision rules only. If a return type carries a borrow and elision cannot pick its input, lust rejects the function. Rust would need a lifetime name there.
- Region inference in a body is NLL-style, with **two-phase borrows**, the same as Rust. Without two-phase borrows, `v.push(v.len())` fails, and agents write that all the time.
- Closures whose parameters are references are a known hard area. In v1, such closures can only be passed to built-in iterator adapters and std methods.

User code has no lifetime names, but the checker still needs real lifetime logic inside. Std signatures use it: `Iter<'a, T>::next` returns a borrow tied to the iterator, `Fn(&str)` is higher-ranked, and drop check applies to std containers that hold borrows. The checker is smaller than rustc's, but it is not small. Phase 2 M3 is budgeted for this.

Negative tests come before features. Each rule above gets programs that must fail, including nested containers, reborrows, partial moves, and borrowed closure captures.

## Traits and inference

- Type inference is local to one body: unification plus a queue of trait obligations, the same shape as rustc.
- **One-candidate rule:** the solver selects an impl only when `Self` and all trait input parameters are known. Associated type outputs can still be unknown. Then at most one impl can match, so the solver never searches or backtracks. Example: `String: Borrow<_>` waits until `get("hammer")` gives `Borrow<str>`.
- An obligation that is not ready waits in the queue. If it is still not ready at the end of the body, lust asks for a type annotation.
- Method lookup uses Rust's autoderef order: at each deref step, try by value, then `&`, then `&mut`. This is how `parts.get(0)` finds the slice method through `Deref`, and how `parse` works on a `&&str`.
- Integer literals fall back to `i32` and float literals to `f64`, the same as Rust. Closure parameter types come from the expected `Fn` signature, for example from `Iterator::Item`.
- Users cannot write blanket impls (`impl<T: X> Y for T`), overlapping impls, or specialization.
- The std has compiler-known traits and blanket impls that users cannot write. Some of them: `From<T> for T`, `From` gives `Into`, `Display` gives `ToString`, `Display` and `Debug` for `&T`, `Borrow<T> for T`, `Borrow<str> for String`, `Iterator` gives `IntoIterator`. Also `FromIterator`, `FromStr`, `Deref`, `Fn`/`FnMut`/`FnOnce`, `Send`, `Sync`, `Copy`, and `Sized`.
- Associated types are normalized once the obligation is ready. In v1, only std traits can declare associated types.
- `dyn Trait` comes later.
- Phase 4 includes a traced solver test that type-checks the syntax sample step by step.

## Generics

- Plan: monomorphize in dev builds, the same as Rust. This is provisional until the Phase 0 mono-size spike.
- Limits: an instantiation depth limit of 128, the same as rustc's recursion limit. Also a total instance limit and a type size limit, because a short generic program can branch into thousands of instances. Polymorphic recursion such as `fn f<T>(x: T) { f(vec![x]) }` fails in both compilers.
- Plan B, if the build budget fails: dictionary passing in dev builds. That needs a full design first: erased calling convention, generic local storage, layout, alignment, and drop.

## Threads (v1)

- v1 has `std::thread::spawn`, `JoinHandle::join`, `Arc`, `Mutex`, and `mpsc` channels.
- The `spawn` closure and its return type must be `Send` and must not carry borrows. The compiler checks this through captures and generic arguments, at any depth. This is stricter than Rust: Rust accepts `'static` borrows such as a `Vec<&str>` of string literals. The error tells the agent to use `String`.
- `spawn` only works in non-generic code. Lust has no `'static` bound syntax, so a generic `T` cannot prove it carries no borrows. The error tells the agent to use a concrete type.
- `Send` and `Sync` are computed from fields, plus a fixed table for std types. Some entries: `Rc` is neither. `RefCell` is not `Sync`. `MutexGuard` is not `Send`. `Arc<T>` is both if `T` is `Send + Sync`. `Mutex<T>` is both if `T` is `Send`. Users cannot implement `Send` or `Sync`.
- Runtime: pthreads. `Arc` counts use C11 `stdatomic.h` from `tcc` mob, so they work on x86_64 and arm64.
- Later: `RwLock`, public atomics, `thread::scope`.

## What lust rejects

Each error tells the agent what to do instead. The `fix` text is part of the error design.

```lust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}
```

```json
{
  "code": "L0201",
  "severity": "error",
  "message": "struct fields cannot hold references",
  "at": "src/parse.rs:2:12",
  "fix": "Store an owned String in the struct, or keep only `pos: usize` and pass `input: &str` to each method."
}
```

| Rust feature | Lust error says |
|---|---|
| `'a` lifetime syntax, `'static` bounds | Remove it. If elision is ambiguous, return an owned value or an index. |
| `macro_rules!`, proc macros | Write a function. Built-in macros only. |
| `impl<T: X> Y for T` | Implement `Y` for each concrete type. |
| `Wrapper<&str>` (a user generic type with a borrow inside) | Use an owned type such as `Wrapper<String>`, or a std type such as `Option<&str>`. |
| `fn f() -> impl Trait` | Return a concrete type or an enum. |
| `dyn Trait` | Not supported yet. Use an enum or generics. |
| `thread::spawn` in a generic function | Move the spawn into a non-generic function. |
| `std::any::type_name` | Not supported. Its output text is not stable in Rust. |
| `async`, `await` | Not supported. Use `std::thread` and channels. |
| `unsafe` | Not supported. |

## Semantics

- **Ownership and moves:** same as Rust.
- **Panics:** a single-file build aborts: a panic in any thread ends the process. A Cargo crate target uses the dev profile's `panic` setting, unwind by default: `catch_unwind` catches a panic, drops run on unwind, and an uncaught panic in `main` exits 101, as with `cargo build`. `-C panic=unwind|abort` overrides both.
- **Integer overflow** on `+`, `-`, `*`, unary `-`, `pow`, and `abs`: panic in dev, wrap in release. Same as Rust.
- **Shifts** by the bit width or more: panic in dev, mask in release. Same as Rust.
- **Always panic, in both modes:** division or remainder by zero, `MIN / -1`, `MIN % -1`, and out-of-bounds indexing.
- **`as` casts:** integer casts truncate or extend. Float to integer saturates, and NaN becomes 0. Same as Rust.
- **Built-in macros:** `println!`, `print!`, `eprintln!`, `format!`, `vec!`, `assert!`, `assert_eq!`, `assert_ne!`, `panic!`, `todo!`, `unreachable!`.
- **Built-in derives:** `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, `Hash`, `Default`.
- **Modules:** one file is one module. One package per program for now.
- **Tests:** `#[test]` functions. `lust test` runs them.

## Compiler

Written in Rust. The compiler stays small, so its own build time is fine.

```text
files ──parse (parallel)──▶ AST per file
      ──collect──────────▶ signature table (all items, all files)
      ──check (parallel)─▶ typed IR per function + borrow check
      ──mono─────────────▶ list of concrete instances
      ──lower (parallel)─▶ C shards (one per core)
      ──tcc -c (parallel)▶ objects ──tcc──▶ binary
```

Release builds use `rustc -O` on the same source (rule zero). Plan B: send the C to `clang -O2`. That is slow on large monomorphized C.

The front end is data-oriented from day one: flat arrays and indices, not pointer trees; interned types and strings; arena allocation. This is the Zig and Carbon toolchain approach. Check speed comes from the front end, so this is not an optimization for later.

### Backend

Platform tiers:

- **Tier 1:** macOS arm64 and Linux x86_64. Both run the full test suite, the rustc oracle, and the performance budget in CI.
- **Tier 2:** Linux arm64 and macOS x86_64. Full tests, no budget.
- **Later:** Windows.

Stages:

1. **`tcc` mob as a library.** Lust links `libtcc` into the compiler and compiles C in memory. No process spawn, no temp C files. We pin an upstream commit. We fork as `lust-tcc` when we need changes. Expected fork work: overflow builtins, ad-hoc code signing in process on macOS (no `codesign` process per build), and speed work found by profiling.
2. **Own native backend.** Lust IR goes straight to x86_64 and arm64 machine code, in ELF and Mach-O, with an incremental linker that patches the binary in place, the way Zig does. This removes C text generation, C parsing, and the C undefined-behavior class. We start this when Phase 0 or later profiles show that C generation and C parsing are a large part of build time. With monomorphization, they probably will be.

Phase 0 also runs a bake-off: `tcc` mob against Cranelift, on macOS arm64 and Linux, using the same generated workload. Cranelift needs no fork and has no C undefined behavior. If it is close to `tcc` in speed, it can replace stage 1.

Lust IR is designed so the backend can be swapped. The C emitter and a native backend read the same IR.

### C backend rules

The spike shows `tcc` itself is fast. The main risk is undefined behavior in the emitted C.

- Lower each expression to temporaries, in Rust evaluation order. Never pass two calls with side effects as arguments to one C call.
- Emit explicit drop calls. Use drop flags for values that are moved on only some paths.
- Emit inline checks for overflow, shift amount, division by zero, `MIN / -1`, and bounds. `tcc` has no overflow builtins.
- Do wrapping math with unsigned types of at least 32 bits. C promotes `uint16_t` to signed `int`, so `65535 * 65535` on `u16` operands is signed overflow (UB) unless the operands are cast first.
- Float to integer casts go through saturating helpers. Rust gives 4294967295 for `1e30 as u32`. A raw C cast is UB, and `tcc` gives 0.
- Zero-initialize all locals. Keep pointer arithmetic inside runtime helpers.
- Emit `#line` directives so `tcc -g` maps back to `.rs` source. Panic locations come from lust source data, not from C `__LINE__`.
- CI also builds every test with `clang -O2 -fsanitize=address,undefined`.

## Agent interface

- `lust check --json` prints one JSON object per diagnostic, with `code`, `message`, `at`, and `fix`. This ships in compiler v0, not later.
- `lust explain L0201` prints a short page with a good and a bad example.
- No code runs at compile time, so builds are deterministic and easy to cache.
- Later: `lust daemon` keeps the program in memory, and `lust check` uses it when it runs. Changes to a signature, field, or impl must invalidate dependent bodies, not only the changed body.

## Performance budget

These numbers are targets. They become tests after Phase 0 confirms them. After that, if a feature breaks the budget, the feature does not ship.

Conditions: both tier 1 platforms (the 24-core x86_64 Linux dev box, and an Apple Silicon Mac), cold disk cache dropped, a generated program of 100k lines in 200 files. The program must be iterator- and closure-heavy, not only simple functions. The timing harness ships in compiler v0. It records each stage on its own: parse and check, instance discovery, C generation, `tcc`, and link.

| Operation | Target |
|---|---|
| Cold `check` | < 300 ms. Not supported yet: a reviewer measured rustc `check` at about 1.4 s for this size on 24 cores. Phase 0 sets the real number. |
| Cold dev build | < 1 s |
| Warm `check` after a one-line edit (needs the daemon) | < 50 ms |

## Syntax eval

Two rounds. Each round asks one clear question.

### Round 1: does the lust subset hurt agents?

Runs in Phase 1, before the compiler exists.

- **Conditions:** full Rust vs. the lust subset. Both are checked by rustc. The subset also runs a small subset linter, and its errors use lust terms and codes.
- Both conditions see rustc errors, so the comparison is fair. The only difference is the subset rules.
- This tells us early what "no references in structs" and "no macros" cost agents.

### Round 2: is Rust-lite better than the Rust subset?

Runs after compiler v0 can check code. Both variants go through lust's own checker, so errors point at the code the agent wrote.

**A. Rust subset.** The syntax above.

**B. Rust-lite.** Rust minus the parts agents get wrong most often:

- String literals are `String`. `&str` only appears in parameters.
- Paths use `.`, not `::`.
- All types auto-derive `Debug`, `Clone`, and `PartialEq` when their fields allow it.

```lust
use std.collections.HashMap;

enum ParseError {
    MissingField(String),
    BadNumber(String),
}

fn label(item: &Item) -> String {
    match item.kind {
        Kind.Tool => "tool",
        Kind.Food { .. } => "food",
    }
}
```

B changes semantics as well as syntax (string literals, auto derives). So round 2 compares two language packages, not syntax only. B also breaks rule zero, so B would need a printer that emits Rust to keep the oracle.

Variant C (parameter modes) is cut. It conflicts with returned references, and it needs a borrow-inserting printer.

### Method, for both rounds

- **Models:** `Muse Wonder Full` (Muse), Claude Opus 5.5, Claude Sonnet 5.5, GPT-6.1-Sol. Pin exact model versions.
- **Tasks:** about 40 small tasks with stdin and stdout tests. Examples: parse a log file, an LRU cache, a tokenizer, a bank account state machine, a graph search.
- **Pilot first:** 10 tasks × 2 conditions × 4 models × 1 run = 80 runs. It finds harness bugs and bad tasks. It also measures variance.
- **Full size:** chosen from pilot variance and the smallest effect we care about. Not fixed in advance.
- **Each run:** a fresh session, randomized task order, one tool (`check`, which builds and runs the tests), at most 8 calls.
- **Statistics:** the unit is the task. Results are paired by task. Confidence intervals are grouped by task.

| Metric | Why |
|---|---|
| Success after each check (k = 1 to 8) | Main score. A curve, not one number, so failed runs still count. |
| Compile failure vs. test failure | Shows if the language or the logic is the problem |
| Wall time per run | What the agent loop actually costs |
| Output tokens | Shorter syntax may cost less |
| Top error codes | Shows which rules agents break most |
| Rust leaks (subset and B only) | Counts Rust features used that the condition does not allow |
