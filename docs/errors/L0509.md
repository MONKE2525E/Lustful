# L0509: glob name whose binding depends on rustc's import order

This is a lust subset rule: the code may be valid Rust, but lust rejects
it on purpose.

rustc resolves glob imports in its own event order. When one name
reaches a module through two or more glob imports (or a glob and a
re-export), some answers depend on that order: which visibility the
name keeps when the globs bring the same item with different
visibility, and which item and visibility an ambiguity carries on to
the next glob importer. lust does not copy rustc's order. It computes
every binding rustc could end with, and it rejects a path or an import
that would get a different answer from one of them: a different item,
private in one and visible in another, a possible ambiguity, or no
binding at all. A `pub use` re-export of such a name is rejected the
same way when the re-export rule passes for one binding and fails for
another.

Fix: import the item explicitly from the module that defines it. An
explicit import wins over every glob, so the order does not matter.
Removing one of the overlapping glob imports also works.

<!-- rustc-wrong: pass -->

## Wrong

```rust
mod shapes {
    pub struct Square;
    impl Square {
        pub fn sides() -> u32 {
            4
        }
    }
}

mod prelude {
    pub use crate::shapes::*;
}

mod geometry {
    pub use crate::shapes::*;
    use crate::prelude::*;
}

fn main() {
    println!("{}", geometry::Square::sides());
}
```

## Fixed

```rust
mod shapes {
    pub struct Square;
    impl Square {
        pub fn sides() -> u32 {
            4
        }
    }
}

mod prelude {
    pub use crate::shapes::*;
}

mod geometry {
    pub use crate::shapes::Square;
    use crate::prelude::*;
}

fn main() {
    println!("{}", geometry::Square::sides());
}
```
