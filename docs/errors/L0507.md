# L0507: ambiguous name from glob imports

Two glob imports bring different items with the same name, and the code
uses that name. The collision is an error only at the use. Import the
item you mean explicitly: an explicit import wins over globs.

The same error applies when a glob import is the only one of the pair.
An import path and a macro call do not let a name a glob brought into an
inner scope shadow a different item in an outer scope: not a module
item, not a prelude name like `Option`, and not an extern crate like
`alloc`. This includes the glob import's own path when the glob brings a
name equal to its first segment (`use a::*;` in a block where module `a`
holds a module also named `a`). An ordinary path in the same place picks
the inner item; only import and macro resolution report the ambiguity.
The same item reached by two paths is never ambiguous.

An ambiguous name reaches a glob importer only when the importer can see
one of the clashing glob imports: two private globs that clash in `c` do
not make the name ambiguous in a module that globs `c` from outside. A
child module (`use super::*`) does see them. An explicit import of an
ambiguous name is an error even when nothing uses the name. While a
module still waits on a single import of a name, its glob binding of
that name does not reach other modules yet, as in rustc.

A `use` path whose first segment is an item of a block that a macro
made (an enum or struct with `#[derive(..)]`, or an item from a macro
call) is ambiguous when any scope outside that block also binds the
name: an outer block, the module, the std prelude, or an extern crate
(rustc E0659). A plain path to the same item is fine.

A plain macro call reads `macro_rules!` definitions in textual scope
first. When a `use` or glob also binds a different macro with that name,
the call is ambiguous unless the `macro_rules!` definition is written in
the same module as that binding (or inside the block of a block-level
`use`), as in rustc E0659.

A macro binding that a macro expansion made (a `macro_rules!` in a
macro's output or input, a `use`, or a `#[macro_export]` definition)
may not shadow a different macro of that name further out: an earlier
`macro_rules!`, one from another call of the same macro, an import, or a
std macro such as `vec` or `matches`. A call inside that same expansion
may use it (rustc E0659, "macro-expanded `macro_rules!`s may not shadow
existing macros").

## Wrong

```rust
mod a {
    pub fn value() -> i64 {
        1
    }
}

mod b {
    pub fn value() -> i64 {
        2
    }
}

use a::*;
use b::*;

fn main() {
    println!("{}", value());
}
```

## Fixed

```rust
mod a {
    pub fn value() -> i64 {
        1
    }
}

mod b {
    pub fn value() -> i64 {
        2
    }
}

use a::*;
use b::*;
use a::value;

fn main() {
    println!("{}", value());
}
```
